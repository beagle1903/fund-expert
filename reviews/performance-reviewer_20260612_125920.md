# Performance Review

**Date**: 2026-06-12
**Reviewer**: Performance Subagent
**Target**: `fundexpert` codebase

## Executive Summary
The `fundexpert` codebase is generally efficient, heavily leveraging vectorized operations in pandas and correctly utilizing `concurrent.futures` for blocking network I/O during Tavily API requests. However, several data-transformation and dataframe-manipulation phases have hidden overheads that, while perhaps unnoticeable on small datasets, could degrade execution times as the universe of funds expands. The most notable performance bottleneck stems from redundant string normalizations on hot paths.

## Findings

### P1: Redundant String Processing (Pipeline vs. Selection)
**Location:** `fundexpert/pipeline.py`, `fundexpert/select/strategy.py`, `fundexpert/select/sector.py`
**Description:** In `pipeline.py` (lines 72-76), `scored_fon_adi_upper` is pre-calculated using vectorized `str.replace` and `.str.upper()`. However, this already-uppercased series is then `.map()`ped over by `bucket_from_name` and `sector_from_name`, both of which invoke `turkish_upper(stripped)` internally. This results in the same Turkish i/ı replacement logic and uppercasing being evaluated multiple times iteratively for every single row.
**Suggested Fix:**
- Remove the internal `turkish_upper` call from `bucket_from_name` and `sector_from_name`, or expose a `_raw` version of these functions that assumes the input is already upper-cased. Alternatively, remove the vectorised preprocessing in `pipeline.py` and strictly rely on the mapping functions. Since vectorised Pandas string operations are faster, the preferred fix is to perform the case-folding exclusively in `pipeline.py` using Pandas, and pass the clean string directly into the mapping dictionaries/loops.

### P1: Full DataFrame Deep Copy Overhead
**Location:** `fundexpert/scoring/score.py`
**Description:** The function `score_candidates` begins by making a deep copy of the dataframe (`out = df.copy()`), before appending the `score` column. For pipelines managing a large number of rows and columns (especially string fields or multiple horizon columns), allocating deep copies adds unnecessary memory and time overhead.
**Suggested Fix:**
- Use a shallow copy `out = df.copy(deep=False)` or use `df.assign(score=...)` which implicitly manages a shallow view while avoiding mutating the original reference.

### P2: Inefficient Column Dropping in Merges
**Location:** `fundexpert/data/merge.py`
**Description:** During universe merging, `buyukluk_keep` and `yonetim_keep` are generated by using `.drop(columns=[...])` to remove identity columns before the inner join. `.drop()` allocates entirely new DataFrames in memory.
**Suggested Fix:**
- Instead of explicitly dropping columns, project only the required columns during the merge: e.g., `df.merge(buyukluk[["fon_kodu", "aum_change_pct", ...]], on="fon_kodu")`. This is significantly more memory-efficient and requires fewer allocations.

### P2: Type Inference Cost in CSV Parsing
**Location:** `fundexpert/data/loader.py`
**Description:** `_read_one` currently relies entirely on Pandas' type inference engine for string and numeric columns. Type inference adds a constant performance penalty to data loading, particularly for strings that contain numeric-like structures.
**Suggested Fix:**
- Supply a `dtype` mapping to `pd.read_csv` for the known non-numeric columns at minimum (e.g., `dtype={"Fon Kodu": str, "Fon Adı": str, "Şemsiye Fon Türü": str}`).

### P2: Suboptimal Row Iteration during Selection
**Location:** `fundexpert/select/pick.py`
**Description:** `pick_top` uses `sorted_df.itertuples(index=True, name='Row')` and subsequently uses `getattr()` or `row.strategy` attribute access in the loop. While `itertuples` is relatively fast, named tuple creation and reflection introduce small overheads per loop iteration.
**Suggested Fix:**
- Switch to using a Python `zip()` over the specific underlying series arrays: `for idx, strategy, sector in zip(sorted_df.index, sorted_df["strategy"], sorted_df["sector"])`. This bypasses tuple construction entirely and allows direct unpacking, making the loop nearly instantaneous.
